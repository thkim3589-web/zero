# 16단계 — 개황도 편집기 전면 개편 (카문다 모델러 참고) + DB 마이그레이션 도입

체크리스트/디자인 개편 이후, 사용자가 개황도(케이블 경로) 그리기 기능 자체가
불편하다며 데스크톱 BPMN 툴인 카문다 모델러의 스크린샷(노드를 클릭하면 바로
옆에 액션 아이콘들이 뜨는 방식)을 보여주고 "이렇게 쉬웠으면 좋겠다"고 요청했다.
이어서 확대/축소/이동, 색상 변경, 선종류 선택, 실제 범례 도형까지 순서대로
요청이 이어져서 한 단계로 묶어 정리한다.

## 1. 점 선택 → 액션 메뉴 (카문다 참고, 1차)

`RouteEditorView`는 원래 점을 "롱프레스하면 조용히 삭제"하는, 화면에 안 보이는
제스처만 지원했다. 이미 찍힌 점을 그냥 탭하면 아무 반응도 없었다 — 죽은 제스처.
`onPointTap` 콜백을 추가해서, 점을 탭하면(드래그 아님) `DiagramEditActivity`가
"종류/이름 변경" / "삭제" 액션 메뉴를 띄우도록 바꿨다. 롱프레스-삭제는 완전히
제거했다 — 이제 모든 조작이 눈에 보이는 메뉴를 거친다.

## 2. 핀치줌 + 팬

`RouteEditorView`에 `Matrix` 기반 확대/축소/이동을 추가했다:
- `ScaleGestureDetector`로 두 손가락 핀치줌 (1~6배, `clampTranslation()`으로
  이미지가 화면 밖으로 완전히 밀려나지 않게 보정).
- 빈 곳을 한 손가락으로 드래그하면 팬(화면 이동) — 이전엔 이 제스처가 아무
  동작도 하지 않는 죽은 제스처였다.
- 더블탭으로 리셋하는 방식은 "탭 한 번"과 구분이 애매해져서 일부러 쓰지 않고,
  대신 눈에 보이는 "확대 초기화" 버튼을 뒀다 (숨은 제스처보다 보이는 버튼을
  선호하는 이번 세션의 일관된 방향).

## 3. 도형 팔레트 — 즉시 배치 모드

카문다처럼 "도형을 먼저 고르고 캔버스를 클릭해서 바로 찍는" 방식을 모바일에
맞게 옮겼다. 캔버스 위 툴바에 4개 아이콘(일반/함체/전주/접속점)을 두고, 하나를
선택하면 그 다음부터 빈 곳을 탭할 때마다 **다이얼로그 없이** 바로 그 종류의
점이 찍힌다. 이름은 "함체-1(임시)"처럼 자동 생성되고, 나중에 점을 탭해서
실제 이름으로 바꾸면 된다 (2번 항목에서 만든 편집 메뉴 재사용). 같은 아이콘을
다시 누르면 선택 해제되어 기존의 "탭 → 다이얼로그로 종류/이름 선택" 방식으로
돌아간다 — 두 방식을 다 남겨뒀다.

## 4. 색상 / 선종류(점선·실선) 사용자 지정

기존엔 신설=파랑, 철거=빨강으로 고정이었다. `RouteLine`에 `dashed: Boolean`
필드를 추가하고, 색상 7종(실제 범례에서 실제로 쓰는 색만 — 빨강/파랑/자홍/
초록/노랑/검정/주황) 중 고를 수 있는 팔레트와 실선/점선 토글을 툴바에 뒀다.
둘 다 `RouteLine`에 저장되어 다음에 열어도 유지된다.

## 5. 실제 범례 심벌(P/C 문자기호 + 상태색) 반영

13단계에서 확인한 진짜 개황도 범례는 "모양=시설물 종류(P=함체, C=전주 등),
색상=상태(신설=파랑/기설=노랑/철거=검정)"의 2축 체계라는 게 문서로 남아있었다.
지금까지는 사각형/삼각형 같은 임의 도형+라인색으로 근사했는데, 이번에 실제
체계에 맞춰 다시 만들었다:

- `RoutePoint`/`EditablePoint`에 `status: MarkerStatus?`(신설/기설/철거) 필드
  추가. `MarkerStatus`는 라벨과 함께 범례 색상(`colorHex`)도 들고 있다.
- 마커 렌더링을 사각형/삼각형 아웃라인에서 **색이 채워진 원형 배지 위에 흰
  글자(P=함체, C=전주)** 로 교체 (`RouteEditorView.drawGlyphMarker` /
  `DiagramCompositor`의 동일 로직) — 실제 범례가 쓰는 "문자기호" 표기를
  흉내낸다.
- 함체/전주를 지정할 때 이름 선택 다음에 상태(신설/기설/철거) 선택 단계가
  추가된다. 도형 팔레트로 즉시 배치할 때는 다이얼로그를 또 띄우면 "즉시 배치"
  취지가 깨지므로 기본값 "신설"로 자동 지정하고, 나중에 점을 탭해 바꿀 수 있게
  했다.
- 접속점(CONNECTION)은 실제 범례에 없는, 이 앱에서 자체적으로 추가한 마커라
  기존 마름모 모양을 그대로 유지했다.

**범위 밖으로 남긴 것**: 실제 범례는 Master/Slave(M/S), 자가/한전/타사 전주
구분, SKB/T·B공동 케이블처럼 더 세분화된 카테고리가 있지만, 이 앱의 데이터
모델(체크리스트의 함체, 구간별 상세의 전주)과 자연스럽게 연결되는 것은
함체(P)/전주(C) 정도라 우선 이 둘만 반영했다.

## 6. DB 마이그레이션 도입 — 스키마 변경으로 인한 데이터 유실 방지

이번 세션에서 스키마를 여러 번 바꾸면서(`fallbackToDestructiveMigration()`만
쓰고 있었음) 버전을 올릴 때마다 **DB 전체**(단가표 포함)가 통째로 삭제되고
있었다. 사용자가 "단가표는 실제로 바뀔 때만 다시 올리고 싶다"고 요청한 것을
계기로 발견 — 별도 기능 요청이 아니라 개발 과정에서 생긴 부작용이었다.

`exportSchema = true` + `room.schemaLocation` gradle 설정을 추가해서 Room이
스키마 JSON을 실제로 내보내게 했고, 거기서 나온 정확한 `CREATE TABLE`문을
그대로 사용해 버전 4→5(ChecklistDetail 전면 재작성 — 이 테이블만 새로 만듦),
5→6(`legendImagePath` 컬럼 추가), 6→7(`dashed` 컬럼 추가), 7→8(`status` 컬럼
추가) 마이그레이션을 작성했다. `fallbackToDestructiveMigration()`은 안전망으로
남겨뒀지만, 이제부터의 스키마 변경은 실제 마이그레이션을 쓰는 게 원칙이다.

## 빌드 검증

각 단계마다 `./gradlew :app:assembleDebug`로 확인. 도중에 Room 컴파일이
kapt 증분 캐시 때문에 새 필드/메서드를 반영 못 하고 이전 버전의
`*_Impl.java`로 컴파일을 시도해 실패한 적이 있었다 — `:app:kaptDebugKotlin
--rerun-tasks`로 강제 재생성해서 해결. 최종 `BUILD SUCCESSFUL`.
